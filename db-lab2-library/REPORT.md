## Вхід і реалізація

Фізична схема описана в [schema.sql](schema.sql), дані - у [seed.sql](seed.sql), вибірки всіх таблиць - у [inspect.sql](inspect.sql). Файли виконуються саме в цьому порядку, у новій окремій базі.

| Таблиця | Стовпці та ключі |
|---|---|
| author | author_id integer PK identity; given_name, family_name, pen_name text NULL |
| edition | edition_id integer PK identity; title, language text NOT NULL; publication_year integer NULL; publisher_name text NULL |
| authorship | author_id integer FK author, edition_id integer FK edition; складений PK (author_id, edition_id) |
| copy | inventory_number integer PK; edition_id integer NOT NULL FK edition |
| reader | reader_id integer PK identity; given_name, family_name, phone text NOT NULL |
| loan | loan_id integer PK identity; reader_id integer FK reader; inventory_number integer FK copy; issued_on, due_on date NOT NULL; returned_on date NULL |

Усі PK додатні. FK не дозволяють видалити об'єкт, на який посилається історія. Телефон не унікальний: спільний сімейний контакт дозволений. Автоматичні номери мають identity; інвентарний номер задає бібліотекар. Невідомий рік або псевдонім зберігається як NULL. Обов'язкові тексти та заповнені необов'язкові тексти не можуть складатися лише з пробілів.

## Бізнес-правила

CHECK перевіряє хоча б одне ім'я автора, додатний рік, строк не раніше видачі й повернення не раніше видачі. Прострочений фактичний возврат дозволений. Частковий унікальний індекс дозволяє лише одну незавершену видачу примірника. Тригер додатково відхиляє перекриття історичних періодів. Дата повернення може дорівнювати даті наступної видачі: спочатку повернення, потім нова видача. Час усередині дня модель не зберігає.

Кардинальності «видання має хоча б один примірник» і «автор має хоча б одне авторство» перевіряють відкладені constraint triggers. Тому видання й його перший примірник додаються однією транзакцією. Зміни дочірніх записів блокують батьківський рядок, щоб паралельні операції не обходили перевірку. Можливий конфлікт блокувань у складних багаторядкових транзакціях: таку транзакцію треба повторити цілком. Тестовий сценарій не потребує права TRUNCATE; це адміністративна операція поза звичайним CRUD.

Доступність і прострочення обчислюються, окремих полів статусу немає. Видача зберігається після повернення. SQL містить додаткові механізми цілісності, тому повторює також бізнес-правила першої роботи, а не лише її прямокутники.

## Повторення

Потрібні PostgreSQL 17, Node.js 22 та окрема порожня база `library_labs`. Можна використати PostgreSQL з Docker Compose курсу. Пароль і порт задаються у своєму середовищі.

```powershell
cd db-lab2-library
npm ci
$env:DATABASE_URL='postgresql://postgres:password123@localhost:5432/library_labs'
node run.cjs schema.sql seed.sql inspect.sql
npm run verify
```

schema.sql не видаляє наявні таблиці й не призначений для повторного створення поверх заповненої бази. Для нового повного прогону створити іншу порожню навчальну базу. inspect.sql і перевірки можна запускати повторно; тестові зміни відкочуються.
